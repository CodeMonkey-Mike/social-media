(https://raw.githubusercontent.com/kaspanet/kips/master/kip-0017.md, read 2026-10-18). The deck line "Brings ZK verification and the covenant machinery" is supported.
- **Plain-language summary the sources support (for the strategist, not a quote):** Toccata (activated June 30, 2026) gave Kaspa's L1 script engine the ability to inspect the spending transaction and restrict its outputs (covenants) plus a consensus-tracked covenant identity. KCC-20 is the shared rulebook, published in the core team's conventions repo, for how a fungible token built from those covenants lays out its state and how a transfer is called, so that wallets, indexers and apps can all recognize the same token the same way. The network enforces the covenant script; the KCC makes implementations agree on its shape.

### Pillar 2: How it works, the four ideas
- **(01) Common interface.** Section 1 "State": "A KCC-20 covenant state describes a token amount, its owner, its borrowing settings, and its extended-state digest." (fields: amount, owner, owner scheme, borrow scheme, borrow guard, extension commitment). Section 2 "Transfer Interface": "The default KCC-20 configuration uses the following transfer entrypoints:" the leader input calls `transfer`, the other inputs call `transfer_delegator`. Rationale: "`KCC20State` uses fixed-width fields" so state arrays encode consistently and other covenants can decode them (https://raw.githubusercontent.com/kaspanet/kccs/main/kcc-0020.md, read 2026-10-18). Helfer's own framing of the goal (kas-smiths opening post, 2026-07-02): "A solid standard should define the minimal identity and interaction surface of a token covenant." and "A KCC20 token is a covenant instance that implements a minimal fungible-token interface." (https://kas-smiths.org/t/fungible-token-covenant-specification-kcc20/8/, read 2026-10-18).
- **(02) Extended state.** Section 4 "State Extendability": "A KCC-20 covenant MAY extend its base state through `extension_commitment`." The state stores only a digest of the extended data; transfers treat that digest as opaque and preserve it (same URL). Michael Sutton on the thread (2026-08-29, as quoted by OriNewman): "The common KCC20 fields remain directly visible onchain" and "implementation-specific state lives behind the extension digest." (kas-smiths page 3, read 2026-10-18). PR #16 "Clarify KCC20 extended state fungibility semantics" merged 2026-08-27 (https://github.com/kaspanet/kccs/pulls?q=is%3Apr, read 2026-10-18).
- **(03) Flexible authority through KCC-2.** KCC-2 "Authority Schemes" (authors Romain Billot (@IzioDev), Michael Sutton; Status Last Call; Created 2026-08-20; Requires KCC-1, KIP-20). An authority can be a public key, key commitment, program, or covenant lineage, "whose approval may be required for an application operation." Scheme table: `0x00` p2pk-schnorr/v1 (32-byte Schnorr public key); `0x01` p2pkh-schnorr/v1 (hash of the key); `0x02` p2pkh-ecdsa/v1 (hash of a 33-byte ECDSA key); `0x03` p2sh/v1 (one exact P2SH redeem script); `0x04` covenant-id/v1 (a KIP-20 Covenant ID, "One continuing covenant lineage"); `0x05` to `0x7f` reserved, `0x80` to `0xff` custom (https://raw.githubusercontent.com/kaspanet/kccs/main/kcc-0002.md, read 2026-10-18). In KCC-20, "the owner field is defined by KCC-2" and "These layouts apply KCC-2's minimum approval checks." (kcc-0020.md sections 1 and 2). So the brief's four controllers (a public key, a key commitment, a script, another covenant) map to schemes 0x00, 0x01/0x02, 0x03, 0x04: supported.
- **(04) Borrowed Receive.** KCC-20 section 5 opens: "Receiving tokens normally means creating a new UTXO and funding it with KAS." Borrowed receive lets the sender reuse an existing compatible token UTXO and raise its amount while the owner and extended state stay the same; the KAS value must not drop below the borrowed input's value (kcc-0020.md, read 2026-10-18). The companion guide: KIP-9 "prices UTXO-set growth through storage mass, which rises for small-valued new outputs."; on the recreated UTXO "the KAS value cannot decrease, and the owner and extended state remain unchanged."; "Each KCC-20 state contains a `borrow_scheme` and a 32-byte `borrow_guard`."; "`borrow_scheme` selects the authorization rule, while `borrow_guard` holds its parameter or evolving state."; schemes include `disabled/v1`, `amount-threshold/v1` ("allows any sender to borrow when the token increase exceeds the effective threshold."), `schnorr-signature/v1`, `hash-chain/v1` (https://raw.githubusercontent.com/kaspanet/kccs/main/kcc-0020/borrowed-receive-authorization.md, read 2026-10-18). Storage mass itself: KIP-9 "Extended mass formula for mitigating state bloat" (authors Michael Sutton, Ori Newman, Shai Wyborski, Yonatan Sompolinsky; Active) introduces "a new quantity called the `storage_mass`"; tiny outputs are "heavily charged" (https://raw.githubusercontent.com/kaspanet/kips/master/kip-0009.md, read 2026-10-18). NOTE for the brief's wording: the spec says the KAS value "cannot decrease" (a floor), not "stays put"; the owner does stay unchanged. The spec text itself never uses the words "storage mass"; the companion guide does.
- **Why Borrowed Receive needed hardening (timeline color):** PR #18 "KCC-0020: prevent hash-chain borrow front-running" merged 2026-08-28; Kaspalytics (2026-08-14) on a related draft bug: "On August 11 the contributor Shawn reported that a byte-saving shortcut he had proposed days earlier" would "let anyone mint tokens with no signature at all" and was "fixed it in three bytes before anyone built on it" (https://buttondown.com/kaspalytics/archive/issue-2-reading-a-99-drop-a-spec-authors-own-mint/, read 2026-10-18). Optional; a caveat line, not a section.

### Pillar 3: KCC-20 vs KRC-20 (the marquee contrast)
- **Origin, KCC-20:** published in `kaspanet/kccs`; authors include Michael Sutton (author of KIP-14, KIP-20; co-author KIP-2, KIP-9) and Ori Newman (author of KIP-17; co-author KIP-9) (KCC-20 header; KIP headers; read 2026-10-18). **What Last Call means (KCC-0 section 4.2, read 2026-10-18):** lifecycle Idea, Draft, Review, Last Call, Final. Last Call: "The final review window."; an editor assigns it and sets a `Last-Call-Deadline`, "typically 14 days later."; if normative changes are needed the KCC returns to Review. Final: an ecosystem convergence point; later edits limited to errata and non-normative clarifications. Finalization criteria for Standards Track: (1) conformance vectors in human-readable and machine-readable form; (2) at least one public implementation passing all machine-readable vectors, linked from the KCC or its PR; (3) "every entry in `Requires` is itself Final (for KCCs) or Active (for KIPs)." Also: a KCC inactive "6 months or greater" moves to Stagnant.
**Dependency chain:** KCC-20 Requires KCC-1, KCC-2, KIP-20. KCC-2 Requires KCC-1, KIP-20. KCC-1 Requires KIP-20, KIP-17 (both Active). So the order is KCC-1 Final, then KCC-2 Final, then KCC-20 can go Final (all three headers, read 2026-10-18).
