How it works

Four ideas carry the standard

01

Common interface

Shared state and transfer conventions. Any wallet, indexer or app can recognize a KCC-20 token, read it and build transfers for it.

02

Extended state

Each token can add its own data and behavior on top. The goal isn't identical tokens. It's one recognizable surface across different deployments.

03

Flexible authority

Through KCC-2, a token can be controlled by a public key, a key commitment, a script, or another covenant. Covenants can own or govern tokens.

04

Borrowed Receive

Every new token UTXO needs KAS under storage-mass rules. Borrowed Receive tops up an existing UTXO instead. Owner and KAS value stay put; only the token amount grows.

Not the same thing

KCC-20 vs KRC-20

OriginKaspa core contributors, kaspanet/kccsKasplex, a third-party protocol
Where balances liveCovenant-enforced UTXOs on L1Data inscribed on L1, read by an indexer

The short version: KRC-20 proved demand for tokens on Kaspa. KCC-20 is the attempt to make them first-class citizens of the base layer.
