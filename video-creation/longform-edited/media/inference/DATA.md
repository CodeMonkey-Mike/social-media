## 2. Pillar facts

### Pillar 1: the definition, by contrast (training once, inference forever)
- **Training** = learning the weights from data. NVIDIA: "Training a neural network, unlike human learning, involves passing data through layered connections"; the post opens with "School's in session. That's how to think about deep neural networks going through the 'training' phase." (https://blogs.nvidia.com/blog/difference-deep-learning-training-inference-ai/, read 2026-10-25).
- **Inference** = the trained network applied to new data. NVIDIA: "This speedier and more efficient version of a neural network infers things about new data" (same post). IBM Research: "Inference is the process of running live data through a trained AI model to make a prediction or solve a task." (https://research.ibm.com/blog/AI-inference-explained, read 2026-10-25).
- **Once vs ongoing.** Raghu Ganti, IBM Research: "Training the model is a one-time investment in compute while inferencing is ongoing" (same IBM page). Training cost scale, same page: training one of today's generative models "can cost millions of dollars in computer processing time".
- **Where the cost accrues (estimates, attribute them).** IBM Research: "up to 90% of an AI-model's life is spent in inference mode"; "But as expensive as training an AI model can be, it's dwarfed by the expense of inferencing." AWS, Jeff Barr, 2019-12-03: "According to what they have told us, inferencing can account for up to 90% of the cost of their machine learning work." (https://aws.amazon.com/blogs/aws/amazon-ec2-update-inf1-instances-with-aws-inferentia-chips-for-high-performance-cost-effective-inferencing/, read 2026-10-25). No measured industry-wide figure was found (Open question 1).
- **Plain-language summary the sources support (for the strategist, not a quote):** training is a one-time compute investment that produces a set of weights; inference is running those frozen weights against new input, every request, for as long as the model is in service; both IBM Research and AWS put inference's share of a model's life or cost at "up to 90 percent", as an estimate.

### Pillar 2: what one LLM request actually does
- **Tokens, and the model sees token IDs.** The Hugging Face guide's own generation loop starts with `input_ids = tokenizer(prompt, return_tensors="pt")["input_ids"]` and feeds the model only those ids, appending each sampled `next_token_id`; the text comes back through `tokenizer.batch_decode(...)` (https://huggingface.co/docs/transformers/main/en/llm_tutorial_optimization, section 3.2, read 2026-10-25). Billing is per token: Anthropic prices "Base input tokens" and "Output tokens" per MTok; OpenAI "Prices per 1M tokens." (section 5). Anthropic also notes tokenizers differ: the Claude 4.7-and-later tokenizer "produces approximately 30% more tokens for the same text" than the previous one (pricing page, read 2026-10-25).
- **Autoregressive = one token at a time, each depending on the ones before.** Hugging Face: "Auto-regressive text generation with LLMs works by iteratively putting in an input sequence, sampling the next token, appending the next token to the input sequence, and continuing to do so until the LLM produces a token that signifies that the generation has finished." (same guide, section 3.2). NVIDIA: "In the decode phase, the LLM generates output tokens autoregressively one at a time, until a stopping criteria is met." (https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/, Shashank Verma and Neal Vaidya, 2023-11-17, read 2026-10-25).
- **PREFILL (the prompt, in parallel, compute-bound).** NVIDIA: "In the prefill phase, the LLM processes the input tokens to compute the intermediate states (keys and values)"; the post describes it as a parallel workload that "effectively saturates GPU utilization" (same NVIDIA 2023 post). vLLM's optimization docs label the two phases directly: "compute-bound (prefill) and memory-bound (decode)" (https://docs.vllm.ai/en/latest/configuration/optimization.html, "Chunked Prefill", read 2026-10-25).
- **The KV cache.** NVIDIA: "To avoid recomputing all these tensors for all tokens at each time step, it's possible to cache them in GPU memory." and "Growing linearly with batch size and sequence length, the memory requirement can quickly scale." (same NVIDIA 2023 post). Hugging Face: tokens "never depend on later tokens", so "one can therefore cache each layer's key-value vectors for all previous timesteps"; with the cache "The maximum required memory is not increased quadratically with the number of generated tokens, but only increases linearly." and "One should always make use of the key-value cache as it leads to identical results and a significant speed-up for longer input sequences." (HF guide, section 3.2). Size example from the same guide: for `bigcode/octocoder` at a 16,000-token input, "Roughly 8 billion float values! Storing 8 billion float values in float16 precision requires around 15 GB of RAM which is circa half as much as the model weights themselves!"
- **DECODE (one token per step, memory-bandwidth-bound, re-reads the cache).** NVIDIA: "In other words, this is a memory-bound operation." (same NVIDIA 2023 post, decode phase). Hugging Face: "In auto-regressive decoding, large key-value vectors need to be reloaded, concatenated with the current key-value vector pair ... at every step. For auto-regressive decoding, the required memory bandwidth for the constant reloading can become a serious time bottleneck." (HF guide, section 3.2.2). NVIDIA benchmarking post: attention during generation "is generally not compute-bound" and "A longer OSL will increase the memory requirement (both bandwidth and capacity) for the generation stage" (https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts, Vinh Nguyen, Wenwen Gao, Emily Apsey, Ganesh Kudleppanavar, Neelay Shah and Elias Bermudez, 2025-04-02, read 2026-10-25).
- **The two latency numbers.** NVIDIA 2025-04-02: "Time to first token (TTFT) is the time it takes to process the prompt and generate the first token"; "A longer ISL will increase the memory requirement for the prefill stage and thus increase the TTFT."; "Intertoken latency (ITL) is the average time between the generation of consecutive tokens in a sequence." and "It is also known as time per output token (TPOT)."; ITL is measured "so that ITL is a characteristic of the decoding part of the request processing only." (same post). So: TTFT belongs to prefill, ITL/TPOT to decode, as the brief states.
- **Plain-language summary the sources support (for the strategist, not a quote):** text becomes token IDs; prefill reads every prompt token at once and writes the keys and values into the KV cache (the GPU is busy computing); decode then produces one token per step, each step reloading the whole cache (the GPU is waiting on memory); the user feels prefill as time to first token and decode as time per output token.

### Pillar 3: the levers that make it fast and cheap
- **Continuous (in-flight) batching.** Origin: Orca, OSDI 2022, Gyeong-In Yu et al.: "we propose iteration-level scheduling, a new scheduling mechanism" that "schedules execution at the granularity of iteration (instead of request)", reported as a "36.9× throughput improvement at the same level of latency" over NVIDIA FasterTransformer (https://www.usenix.org/conference/osdi22/presentation/yu, read 2026-10-25; the page text renders the figure as "36:9×", a formatting artefact). NVIDIA 2023: "many LLM serving solutions include an optimized scheduling technique called continuous or in-flight batching." and "With in-flight batching, rather than waiting for the whole batch to finish before moving on to the next set of requests" finished sequences leave the batch and new requests join while others are still running (NVIDIA 2023 post). vLLM lists "Continuous batching of incoming requests, chunked prefill, prefix caching" as a feature (https://docs.vllm.ai/en/latest/, read 2026-10-25); with chunked prefill "the scheduling policy prioritizes decode requests" (vLLM optimization page).
- **KV cache management: PagedAttention.** Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention", arXiv:2309.06180, submitted 2023-09-12, SOSP 2023: "existing systems struggle because the key-value cache (KV cache) memory for each request is huge" and "grows and shrinks dynamically"; "When managed inefficiently, this memory can be significantly wasted by fragmentation and redundant duplication"; vLLM achieves "near-zero waste in KV cache memory and (2) flexible sharing of KV cache within and across requests"; "vLLM improves the throughput of popular LLMs by 2-4×" at "the same level of latency compared to the state-of-the-art systems, such as FasterTransformer and Orca." (https://arxiv.org/abs/2309.06180, read 2026-10-25). vLLM describes itself as "a fast and easy-to-use library for LLM inference and serving" with "Efficient management of attention key and value memory with PagedAttention" (https://docs.vllm.ai/en/latest/).
- **Prefix caching (self-hosted) / prompt caching (hosted).** vLLM: "Automatic Prefix Caching (APC in short) caches the KV cache of existing queries, so that a new query can directly reuse the KV cache if it shares the same prefix with one of the existing queries, allowing the new query to skip the computation of the shared part." (https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html, read 2026-10-25). Anthropic: "Prompt caching optimizes your API usage by allowing resuming from specific prefixes in your prompts."; "Cache read tokens are 0.1 times the base input tokens price"; "Cache write tokens with a 5-minute TTL are 1.25 times the base input tokens price."; "By default, the cache has a 5-minute lifetime." (https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching, read 2026-10-25; the per-model exceptions, 0.025x and 0.05x on the newest models, are in section 5).
- **Quantization (FP16/BF16 to 8 or 4 bit).** Hugging Face: "Loading the weights of a model having X billion parameters requires roughly 2 * X GB of VRAM in bfloat16/float16 precision"; "model weights can be quantized to 8-bit or 4-bits without a significant loss in performance (see Dettmers et al.)"; worked example `bigcode/octocoder`: 29.0 GB peak in bfloat16, 15.2 GB in 8-bit, 9.5 GB in 4-bit; "4-bit quantization allows the model to be run on GPUs such as RTX3090, V100, and T4". The same guide warns: "inference time is often not reduced when using quantized weights, but rather increases" (with the bitsandbytes dequantize-on-the-fly scheme) and "model quantization trades improved memory efficiency against accuracy and in some cases inference time." (HF guide, section 1, read 2026-10-25). llama.cpp offers "1.5-bit, 2-bit, 3-bit, 4-bit, 5-bit, 6-bit, and 8-bit integer quantization for faster inference and reduced memory use" (https://github.com/ggml-org/llama.cpp, read 2026-10-25). vLLM lists "Quantization: FP8, MXFP8/MXFP4, NVFP4, INT8, INT4, GPTQ/AWQ, GGUF, compressed-tensors, ModelOpt, TorchAO, and more" (https://docs.vllm.ai/en/latest/).
- **Speculative decoding.** Leviathan, Kalman, Matias (Google), "Fast Inference from Transformers via Speculative Decoding", arXiv:2211.17192, v1 2022-11-30, ICML 2023 oral: "an algorithm to sample from autoregressive models faster without any changes to the outputs", "by running them in parallel on the outputs of the approximation models, potentially generating several tokens concurrently", "a 2X-3X acceleration compared to the standard T5X implementation" on T5-XXL "with identical outputs" (https://arxiv.org/abs/2211.17192, read 2026-10-25). NVIDIA 2023: "The basic idea of this approach is to use some 'cheaper' process to generate a draft continuation" which the main model verifies in parallel. vLLM: "Speculative decoding including n-gram, suffix, EAGLE, DFlash" (https://docs.vllm.ai/en/latest/).
- **The inference engine, the layer between request and GPU.** vLLM: "a fast and easy-to-use library for LLM inference and serving" (https://docs.vllm.ai/en/latest/). SGLang: "an open-source inference framework for large language, vision-language, and diffusion models, optimized for agentic workloads, large-scale serving, and RL rollouts" (https://github.com/sgl-project/sglang, read 2026-10-25). TensorRT-LLM: "TensorRT LLM optimizes inference for LLMs and Visual Gen models with specialized kernels for common operations, an efficient runtime, and a pythonic framework", with "algorithmic runtime optimizations (Prefill-Decode disaggregation, Wide Expert Parallelism, Speculative Decoding, etc)" (https://github.com/NVIDIA/TensorRT-LLM, read 2026-10-25). Ollama: "Ollama has a REST API for running and managing models" served at `http://localhost:11434`, on the "llama.cpp project founded by Georgi Gerganov" as its backend (https://github.com/ollama/ollama, read 2026-10-25). llama.cpp: "LLM inference in C/C++", "The main goal of llama.cpp is to enable LLM (and VLM) inference with minimal setup and state-of-the-art performance" (https://github.com/ggml-org/llama.cpp).
- **Hosted (pay per token) vs self-hosted (pay for the GPU).** Hosted side is primary (section 5 prices). Self-hosted side: the model has to fit the card (HF rule of thumb above; Whisper's own VRAM table in pillar 4), and the engine's job is to keep the card busy (continuous batching above). NO primary source gives a crossover point (requests per day, utilisation percent) at which self-hosting becomes cheaper; keep that line CONDITIONAL ("worth it when the GPU stays busy") and never a number. See Open question 2.

### Pillar 5: the 2026 angle, reasoning models spend inference-time compute
- **OpenAI reasoning guide** (https://developers.openai.com/api/docs/guides/reasoning, read 2026-10-25): "Reasoning models use internal reasoning tokens before producing a response."; "While reasoning tokens are not visible via the API, they still occupy space in the model's context window" and "are billed as output tokens"; "the models may generate anywhere from a few hundred to tens of thousands of reasoning tokens"; effort: "The reasoning.effort parameter guides the model on how much to think when performing a task."; "Supported values are model-dependent and can include none, minimal, low, medium, high, xhigh, and max."; "Lower effort favors speed and lower token usage, while at higher effort the model thinks more completely"; xhigh: "Only use when your evals show a clear benefit that justifies the extra latency and cost."
- **Anthropic extended thinking** (https://platform.claude.com/docs/en/docs/build-with-claude/extended-thinking, read 2026-10-25): "The `budget_tokens` parameter sets a target for how many tokens Claude can use for its internal reasoning process. Larger budgets can improve response quality by allowing more thorough analysis for complex problems."; "Thinking tokens count toward the `max_tokens` limit for the turn"; "Higher budgets allow more comprehensive reasoning, with diminishing returns that depend on the task, and at the cost of increased latency."; the response's "`usage.output_tokens_details.thinking_tokens` field ... reports how many of the billed output tokens were internal reasoning." Status note on the page: manual `budget_tokens` is deprecated on Claude 4.6 and rejected on 4.7 and later; the replacement is `thinking: {type: "adaptive"}` with `output_config: {effort: ...}`, where "at lower effort settings it might skip thinking entirely on easy inputs." Either way the thinking is output tokens on the inference bill.
- **Jensen Huang, NVIDIA GTC 2025 keynote, 2025-03-18 (YouTube `_waPvOwL9Z8`, words transcribed locally from the audio, section 6):** at 12:54 to 13:08: "The amount of computation we need at this point as a result of agentic AI, as a result of reasoning, is easily a hundred times more than we thought we needed this time last year."; at 15:19 to 15:23: "instead of just generating one token or one word after next, it generates a sequence of words that represents a step of reasoning."; at 16:02 to 16:18: "ten times tokens, ten times faster, the amount of computation we have to do is ten, a hundred times more easily ... the amount of computation we have to do for inference is dramatically higher than it used to be."; at 54:18 to 54:24: "it is the ultimate extreme computing problem and it's called inference." (context: a vendor CEO projecting demand for his own chips; see section 6 context checks and Do-not-air row 11).
- **Plain-language summary the sources support (for the strategist, not a quote):** a reasoning model emits extra tokens before its answer; both OpenAI and Anthropic bill those as output tokens, and both expose an effort knob that trades latency and cost for depth; so the cost of one request now varies with how hard the model thinks, and that variable bill lands on inference.
