# Command Reference

All commands follow this pattern:

```bash
purr <command> [args]
```

***

## purr wallet address

Get your wallet address.

```bash
purr wallet address --chain-type ethereum
```

Returns JSON with your wallet address.

***

## purr wallet balance

Check native or token balance.

```bash
purr wallet balance
```

***

## purr wallet transfer

Transfer native tokens or ERC-20s to a recipient.

```bash
purr wallet transfer --to <address> --amount <amount> --token <symbol>
```

***

## purr wallet sign

Sign a message with your wallet.

```bash
purr wallet sign --message "authenticate:user123"
```

***

## purr wallet sign-typed-data

Sign EIP-712 typed data.

```bash
purr wallet sign-typed-data --data <json>
```

***

## purr execute

Execute transaction steps from a file.

```bash
purr execute --file <steps.json>
```

***

## purr pancake swap

Swap tokens via PancakeSwap.

```bash
purr pancake swap --execute
```

***

## purr dflow swap

Swap tokens on Solana via DFlow.

```bash
purr dflow swap --execute
```

***

## purr bitget swap

Multi-chain EVM swaps via Bitget.

```bash
purr bitget swap --execute
```

***

## purr lista deposit

Deposit into Lista DAO vaults.

```bash
purr lista deposit --execute
```

***

## purr lista list-vaults

List available Lista vaults.

```bash
purr lista list-vaults
```

***

## purr fourmeme buy

Buy tokens on Four.meme.

```bash
purr fourmeme buy --execute
```

***

## purr config

Manage your purr configuration.

```bash
purr config set api-url "https://purr.pieverse.io"
purr config set api-token "<token>"
purr config set instance-id "<id>"
purr config list
```

Config is read from environment variables (`WALLET_API_URL`, `WALLET_API_TOKEN`, `INSTANCE_ID`) or from values set via `config set`. Environment variables take precedence.

# External OpenClaw

If you're running your own OpenClaw instance (not hosted on purrfect-claw-platform), set up purr by following these steps in order.

## Step 1 — Authenticate

Choose an authentication method:

|                    | API Key                   | Social Login                     |
| ------------------ | ------------------------- | -------------------------------- |
| **Human needed?**  | No                        | Yes — human approves via OAuth   |
| **Auth type**      | Static key (`pcp_live_*`) | JWT access token + refresh token |
| **Token validity** | Permanent (until revoked) | Access: 1 hour, Refresh: 7 days  |
| **Best for**       | Autonomous agents         | Agents with a human owner        |

**If you're unsure, use Option A.**
### Option A: API Key

Register your agent — no account required:

```bash
curl -sf -X POST "https://purr.pieverse.io/v1/agents/register" \
  -H "Content-Type: application/json" \
  -d '{"name": "my-agent", "chainType": "ethereum"}'
```

Response:

```json
{
  "ok": true,
  "data": {
    "agentId": "abc12345-...",
    "apiKey": "pcp_live_...",
    "wallet": { "address": "0x...", "chainId": 56, "chainType": "ethereum" }
  }
}
```

> **Warning:** Save your `apiKey` immediately — it is shown only once.

Write credentials to `~/.purrfectclaw/.env`:

```bash
mkdir -p ~/.purrfectclaw
cat > ~/.purrfectclaw/.env << 'EOF'
AGENT_ID=<agentId from response>
API_KEY=<apiKey from response>
AUTH_TOKEN=$API_KEY
WALLET_ADDRESS=<wallet.address from response>
WALLET_API_URL=https://purr.pieverse.io
WALLET_API_TOKEN=<apiKey from response>
INSTANCE_ID=<agentId from response>
EOF
```
### Option B: Social Login

**Step B1 — Initiate the device flow**

```bash
curl -sf -X POST "https://purr.pieverse.io/v1/auth/device" \
  -H "Content-Type: application/json"
```

Response:

```json
{
  "ok": true,
  "data": {
    "deviceCode": "...",
    "loginUrl": "https://purr.pieverse.io/v1/auth/sso?device_code=...",
    "expiresIn": 600,
    "interval": 5
  }
}
```

**Step B2 — Show the login URL to your owner**

Display the `loginUrl` to the owner. They sign in with Google and see a success page.

**Step B3 — Poll for the result**

Poll every 5 seconds until login completes:

```bash
curl -sf -X POST "https://purr.pieverse.io/v1/auth/device/token" \
  -H "Content-Type: application/json" \
  -d '{"deviceCode": "<deviceCode from step B1>", "chainType": "ethereum"}'
```

While pending, you'll get HTTP 428 with `"authorization_pending"`. On success:

```json
{
  "ok": true,
  "data": {
    "accessToken": "eyJ...",
    "instanceId": "...",
    "user": { "id": "...", "email": "...", "name": "..." },
    "wallet": { "address": "0x...", "chainId": 56, "chainType": "ethereum" }
  }
}
```

Write credentials to `~/.purrfectclaw/.env`:

```bash
mkdir -p ~/.purrfectclaw
cat > ~/.purrfectclaw/.env << 'EOF'
ACCESS_TOKEN=<accessToken from response>
REFRESH_TOKEN=<refreshToken from response>
AUTH_TOKEN=$ACCESS_TOKEN
INSTANCE_ID=<instanceId from response>
WALLET_ADDRESS=<wallet.address from response>
WALLET_API_URL=https://purr.pieverse.io
WALLET_API_TOKEN=<accessToken from response>
EOF
```

> **Note:** Access tokens expire after 1 hour. Use `POST /v1/auth/refresh` with your refresh token to renew without re-authenticating.
Source your credentials:

```bash
source ~/.purrfectclaw/.env
```

## Step 2 — Download skills

```bash
mkdir -p ~/.purrfectclaw/skills
curl -sf "https://purr.pieverse.io/v1/skills/bundle" \
  -H "Authorization: Bearer $AUTH_TOKEN" \
  -o /tmp/skills-bundle.tar.gz
tar xzf /tmp/skills-bundle.tar.gz -C ~/.purrfectclaw/skills
```

## Step 3 — Install and configure purr

See [Installation](/cli/installation) for the full install steps. Then configure:

```bash
purr config set api-url "https://purr.pieverse.io"
purr config set api-token "$AUTH_TOKEN"
purr config set instance-id "$INSTANCE_ID"
```

Verify:

```bash
purr config list
```

## Step 4 — Register skills with OpenClaw (OpenClaw-hosted agents only)

> **Note:** Skip this step if you are running a standalone agent without an OpenClaw gateway.

```bash
CURRENT=$(openclaw config get skills.load.extraDirs 2>/dev/null)
MERGED=$(node -e "
const cur = (() => { try { return JSON.parse('${CURRENT:-[]}'); } catch { return []; } })();
const p = '~/.purrfectclaw/skills';
if (cur.indexOf(p) === -1) cur.push(p);
console.log(JSON.stringify(cur));
")
openclaw config set skills.load.extraDirs "$MERGED"
```

## Step 5 — Verify

```bash
purr wallet address --chain-type ethereum
# Expected: returns JSON with your 0x wallet address
```

For OpenClaw-hosted agents, restart the gateway and verify skills loaded:

```bash
openclaw gateway restart
openclaw skills list
```

# Purr-fect Claw

If your OpenClaw agent runs on a **purrfect-claw-platform** instance, purr is pre-installed and pre-configured. There is nothing to set up.

## What happens automatically

When your container starts, the platform injects:

* `WALLET_API_URL` — the platform's wallet endpoint
* `WALLET_API_TOKEN` — your auth token
* `INSTANCE_ID` — your unique instance identifier, mapped to your TEE wallet

The purr CLI reads these at runtime. Your wallet identity is wired in before your first command runs.

## Running your first command

```bash
purr wallet address --chain-type ethereum
```

Your wallet address is returned immediately.

## Using purr in a skill

Call purr commands from within your skill's execution instructions. For example, a balance-check skill might instruct the agent to run:

```bash
purr wallet balance
```

The agent executes this in the container, reads the output, and uses the balance in its response.

## No manual configuration needed

You do not need to run `purr config set`. The environment variables injected by the platform take precedence over any config file values. If you run `purr config list`, you'll see values sourced from the environment.

# Installation

## Install purr

Install the purr CLI from GitHub Releases:

```bash
curl -fsSL https://raw.githubusercontent.com/Pieverse-Eng/purr-cli/main/install.sh | bash
```

This installs the `purr` binary to `~/.purrfectclaw/bin/purr`.

To pin a specific version:

```bash
curl -fsSL https://raw.githubusercontent.com/Pieverse-Eng/purr-cli/main/install.sh | PURR_VERSION=v0.1.6 bash
```

Verify:

```bash
purr version
```

## Add purr to PATH

```bash
grep -q '.purrfectclaw/bin' ~/.zshrc 2>/dev/null || \
  echo 'export PATH="$HOME/.purrfectclaw/bin:$PATH"' >> ~/.zshrc
```

# Writing Skills

A **skill** is a directory containing a `SKILL.md` file. The file has a YAML frontmatter header and a markdown body describing the skill's tools and execution flows. OpenClaw reads this file to understand what the skill can do and how to invoke it.

## SKILL.md structure

```
my-skill/
└── SKILL.md
```

`SKILL.md` format:

```markdown
---
name: my-skill
description: One-sentence description of what this skill does.
---

# My Skill

(Describe tools, API operations, and how the agent should use them.)
```

## Example: check-balance skill

A skill that reads the user's wallet balance and reports it.

`SKILL.md`:

````markdown
---
name: check-balance
description: Check the user's on-chain wallet balance.
---

# Check Balance Skill

## Tool: check_wallet_balance

Checks the current wallet balance.

### Execution

Run these commands and return the balance output to the user:

```bash
purr wallet balance
```
````

## Example: send-payment skill

A skill that transfers tokens to a specified address.

`SKILL.md`:

````markdown
---
name: send-payment
description: Transfer tokens to a recipient address.
---

# Send Payment Skill

## Tool: send_payment

Transfers assets to a recipient.

### Parameters
- `to` — recipient wallet address
- `amount` — the amount to send
- `token` — token symbol (e.g. `eth`, `usdc`)

### Execution

1. Confirm intent with the user before executing.
2. Run:

```bash
purr wallet transfer --to <to> --amount <amount> --token <token>
```

3. Return the transaction hash from the output.
````

## Using purr in skill execution

Call purr commands exactly as documented in the [Command Reference](/cli/commands). All wallet operations are under `purr wallet <subcommand>`. DeFi operations use their own namespaces (`purr pancake`, `purr lista`, etc.).

# Core Concepts

## The purr wallet

Your purr wallet is TEE-backed. **TEE** stands for Trusted Execution Environment — a hardware-isolated area of a processor where code runs in a secure enclave. Private keys are:

* Generated inside the TEE
* Never written to disk in plaintext
* Never accessible to your skill code, the host OS, or any external party

This means you get a fully programmable wallet with **zero key management**. You don't store secrets. You don't risk leaking keys in skill logic. You just call `purr` and the wallet does its job.

One wallet is provisioned per instance. It is deterministic — the same instance always maps to the same wallet.

## Instances and identity

Every purr command runs in the context of an **instance** — a unique identity that maps to exactly one wallet.

* On **Purr-fect Claw**, your instance identity is injected by the platform as the `INSTANCE_ID` environment variable alongside `WALLET_API_URL` and `WALLET_API_TOKEN`.
* On **external OpenClaw**, your identity is the `agentId` you receive when registering. You set it with `purr config set instance-id <agentId>`.

Both cases use the same underlying mechanism — the CLI sends your identity with every request.

## Authentication

purr supports two auth methods:

* **API Key** (`pcp_live_*`) — a static key tied to an agent identity. Recommended for autonomous agents.
* **JWT access token** — a short-lived token from social login (Google OAuth device flow), tied to a user account. Expires in 1 hour; use `POST /v1/auth/refresh` with your refresh token to renew.

The active token is read from `WALLET_API_TOKEN` (env var) or `purr config set api-token`.

## Credentials file

After registration or login, credentials are stored in `~/.purrfectclaw/.env`:

| Variable           | Purpose                         |
| ------------------ | ------------------------------- |
| `WALLET_API_URL`   | Platform API base URL           |
| `WALLET_API_TOKEN` | Auth token for purr CLI         |
| `INSTANCE_ID`      | Instance ID for purr CLI        |
| `WALLET_ADDRESS`   | Your provisioned wallet address |

## Skills

A **skill** is a directory containing a `SKILL.md` file. Skills are operational instructions loaded into your agent's context — they tell the agent how to route and execute on-chain operations.

The `onchain` skill (downloaded as part of the skills bundle) is the orchestrator. It dispatches to the correct skill for each intent: swap, lend, bridge, buy, etc.

Platform skills are downloaded via:

```bash
curl -sf "https://purr.pieverse.io/v1/skills/bundle" \
  -H "Authorization: Bearer $AUTH_TOKEN" \
  -o /tmp/skills-bundle.tar.gz
tar xzf /tmp/skills-bundle.tar.gz -C ~/.purrfectclaw/skills
```

# Pieverse A2A Overview

Pieverse A2A is an agent-to-agent payment and settlement system built on HTTP 402 Payment Required. It enables agents and merchants to exchange value on-chain with cryptographic proof verification (PoTE — Proof of Transaction Evidence).

1. A **merchant** gates an API endpoint behind a 402 paywall using the Merchant SDK
2. An **agent** hits the endpoint, receives a 402 challenge, authorizes payment via the Agent SDK, and retries
3. The merchant settles the payment on-chain with proof of service delivery
4. For repeated interactions, **payment sessions** aggregate micro-charges into a single on-chain settlement

## Payment Models

### Single Payments

* **Soft verification** — immediate settlement after merchant provides proof
* **Strict verification** — payment is held for a configurable window, allowing the agent to challenge before finalization

### Payment Sessions

Sessions lock a budget that a merchant can charge against incrementally. When the session ends, all charges settle in a single on-chain transaction — reducing gas costs for high-frequency interactions.

## Register as an Agent

Agents are the payer side — they authorize payments and consume paid APIs. Registration gives you an API key and a TEE-secured wallet.

### 1\. Register

```bash
curl -sf -X POST "https://purr.pieverse.io/v1/agents/register" \
  -H "Content-Type: application/json" \
  -d '{"name": "my-agent", "chainType": "ethereum"}'
```

Response:

```json
{
  "ok": true,
  "data": {
"agentId": "...",
"apiKey": "pcp_live_...",
"walletProvisioned": true,
"wallet": { "address": "0x...", "chainId": 56, "chainType": "ethereum" }
  }
}
```

Save the `apiKey` — it is shown only once. The `name` must be globally unique; if taken, the API returns `409`.

### 2\. Use the Agent SDK

```typescript
import { PieverseAgent } from '@pieverse-eng/agent-sdk';

const agent = new PieverseAgent({
  apiKey: process.env.AGENT_API_KEY!,
  cpBaseUrl: 'https://purr.pieverse.io',
});

// Make a paid API call — handles 402 → authorize → retry automatically
const response = await agent.payAndRetry('https://merchant.example/api/data');
```

See the [Agent SDK docs](/pieverse-a2a/agent-sdk) for the full API reference.

## Register as a Merchant

Merchants are the receiver side — they gate endpoints behind 402 paywalls and settle payments.

### 1\. Register

```bash
curl -sf -X POST "https://purr.pieverse.io/v1/agents/register" \
  -H "Content-Type: application/json" \
  -d '{"name": "my-service", "chainType": "ethereum"}'
```

Save the `apiKey` — it is shown only once.

### 2\. Use the Merchant SDK

```typescript
import { PieverseMerchant } from '@pieverse-eng/merchant-sdk';

const merchant = new PieverseMerchant({
  apiKey: process.env.MERCHANT_API_KEY!,
  cpBaseUrl: 'https://purr.pieverse.io',
});

// Gate an endpoint behind a 402 paywall
app.get('/api/data', merchant.middleware402({
  amount: 0.01,
  decimals: 18,
  token: '0x55d398326f99059fF775485246999027B3197955',
  symbol: 'USDT',
  chainId: 56,
  recipient: process.env.MERCHANT_WALLET_ADDRESS!,
  description: 'Premium data access',
}), handler);
```

See the [Merchant SDK docs](/pieverse-a2a/merchant-sdk) for the full API reference.

## SDKs

| Package                                                    | Role     | Description                                            |
| ---------------------------------------------------------- | -------- | ------------------------------------------------------ |
| [`@pieverse-eng/merchant-sdk`](/pieverse-a2a/merchant-sdk) | Receiver | Create 402 challenges, gate endpoints, settle payments |
| [`@pieverse-eng/agent-sdk`](/pieverse-a2a/agent-sdk)       | Payer    | Authorize payments, handle 402 flows, manage sessions  |

## x402 Compatibility

Both SDKs support the [x402 protocol](https://www.x402.org/) via the `PAYMENT-REQUIRED` HTTP header, enabling cross-chain payment interoperability alongside Pieverse's native A2A format.

# Skill Tarball Requirements

## Supported formats

| Format              | Extension         |
| ------------------- | ----------------- |
| Gzip-compressed tar | `.tar.gz`, `.tgz` |
| Zip                 | `.zip`            |
| RAR                 | `.rar`            |

## Size limits

| Limit          | Value               |
| -------------- | ------------------- |
| Archive size   | 5 MB maximum        |
| Extracted size | 50 MB maximum       |
| File count     | 1,000 files maximum |

## Required contents

Your archive must contain **`SKILL.md` at the root** of the extracted directory. The platform rejects archives that are missing this file.

### SKILL.md format

`SKILL.md` must begin with a YAML frontmatter block:

```markdown
---
name: my-skill
description: A one-sentence description of what this skill does.
---

# My Skill

(Rest of the skill documentation...)
```

Both `name` and `description` are required in the frontmatter.

## Security constraints

The platform enforces the following during extraction:

* **No symlinks** — archives containing symbolic links are rejected
* **No path traversal** — files with `../` in their paths are rejected

Violating either constraint results in the upload being blocked with an error.

## Slug format

The slug you choose when uploading must match:

```
^[a-z0-9][a-z0-9-]*$
```

With optional namespace prefix:

```
^[a-z0-9][a-z0-9-]*:[a-z0-9][a-z0-9-]*$
```

**Valid:** `my-skill`, `acme:token-transfer`, `balance-checker`
**Invalid:** `My_Skill`, `../escape`, `acme/skill`

See [Uploading a Skill](/skill-store/uploading-a-skill) for the full upload flow.

## Common errors

| Error                                | Cause                                    | Fix                                               |
| ------------------------------------ | ---------------------------------------- | ------------------------------------------------- |
| `BLOCKED: missing SKILL.md`          | No `SKILL.md` at archive root            | Add `SKILL.md` to the top level of your archive   |
| `BLOCKED: symlink or path traversal` | Archive contains symlinks or `../` paths | Remove all symlinks and relative path entries     |
| `BLOCKED: decompressed too large`    | Extracted content exceeds 50 MB          | Trim large files and unnecessary assets           |
| `BLOCKED: too many files`            | File count exceeds 1,000                 | Reduce the number of files in the archive         |
| `TARBALL_TOO_LARGE`                  | Archive exceeds 5 MB                     | Compress more aggressively or remove large assets |
| `UNSUPPORTED_FORMAT`                 | Unrecognised archive format              | Use `.tar.gz`, `.tgz`, `.zip`, or `.rar`          |

# Uploading a Skill

Once you have a [merchant account](/skill-store/become-a-merchant), you can publish skills directly from the Skill Store UI.

## Upload flow

1. Open the [Skill Store](https://pieverse.io/skill-store) and sign in.
2. Click **My Skills → Upload Skill**.
3. Fill in the required fields:
   * **Slug** — unique identifier for your skill (e.g. `my-skill` or `myorg:my-skill`)
   * **Name** — human-readable display name
   * **Version** — semantic version string (e.g. `1.0.0`)
4. Upload your skill archive (`.tar.gz`, `.tgz`, `.zip`, or `.rar`).
5. Click **Publish**.

The platform validates your tarball, extracts it, and makes the skill available in the store.

## Updating a skill

Upload a new archive with the **same slug**. The upload is idempotent — the existing skill is overwritten. Users who have installed your skill will receive the update on their next sync.

## Slug format

Slugs must match: `^[a-z0-9][a-z0-9-]*$`

You can namespace your skills with a colon: `myorg:my-skill` — the namespaced form matches `^[a-z0-9][a-z0-9-]*:[a-z0-9][a-z0-9-]*$`

Valid examples: `payment-skill`, `acme:token-transfer`, `balance-checker`

## After publishing

Your skill appears in the Skill Store listing immediately after a successful upload. Users can discover and install it into their agents from the store UI.

## Tarball requirements

See [Skill Tarball Requirements](/skill-store/tarball-requirements) for the full spec on what your archive must contain.

## Pay-and-Retry (Recommended)

The simplest way to interact with a 402-gated endpoint is `payAndRetry()`. It handles the entire flow: request → detect 402 → authorize → retry with credential.

```typescript
const response = await agent.payAndRetry('https://merchant.example/api/weather');
const data = await response.json();
```

With strict verification:

```typescript
const response = await agent.payAndRetry('https://merchant.example/api/weather', {
  verification: 'strict',
});
```

`payAndRetry` detects both Pieverse A2A (JSON body) and x402 (`PAYMENT-REQUIRED` header) formats, preferring Pieverse A2A when both are present.

## Manual Authorization

For more control, authorize payments manually:

```typescript
const result = await agent.authorize({
  challengeId: challenge.paymentRequired.challengeId,
  to: challenge.paymentRequired.recipient,
  amountBaseUnits: challenge.paymentRequired.amountBaseUnits,
  token: challenge.paymentRequired.token,
  chainId: challenge.paymentRequired.chainId,
  verification: 'soft', // or 'strict'
});

// result.paymentCredential is a pt_live_* scoped credential
// Use it in X-Pieverse-Payment header on retry
```

### Authorization Options

| Option            | Type                 | Description                                                      |
| ----------------- | -------------------- | ---------------------------------------------------------------- |
| `challengeId`     | `string`             | Challenge ID from the 402 response                               |
| `to`              | `string`             | Merchant wallet address                                          |
| `amountBaseUnits` | `string`             | Amount in base units (wei)                                       |
| `token`           | `string`             | Token contract address                                           |
| `chainId`         | `number`             | Chain ID                                                         |
| `verification`    | `'soft' \| 'strict'` | Verification mode (optional, defaults to `'soft'`)               |
| `mandate`         | `object`             | Optional spending mandate with description, max amount, validity |

## Verification Modes

### Soft (default)

Payment settles immediately after the merchant provides proof. Fast, no hold window.

### Strict

Payment is **held** for a configurable window (default 30 seconds). During the hold window, the agent can challenge the payment if the service was not delivered correctly:

```typescript
const result = await agent.challengePayment(
  credentialId,
  'Service returned incorrect data',
  { expected: 'weather', received: 'error' },
);
```

After the hold window expires without a challenge, the payment auto-finalizes.

## Payment Sessions

For repeated interactions with a merchant, sessions lock a budget that the merchant charges against incrementally. All charges settle in a single on-chain transaction.

### Create a Session

```typescript
import { createHash } from 'node:crypto';

const merchantKeyHash = createHash('sha256')
  .update(merchantApiKey)
  .digest('hex');

const session = await agent.createSession({
  to: '0xMerchantWallet',
  budgetBaseUnits: '50000000000000000', // 0.05 USDT
  token: '0x55d398326f99059fF775485246999027B3197955',
  chainId: 56,
  ttlSeconds: 3600,              // 1 hour
  merchantCredentialHash: merchantKeyHash,
});

console.log(session.sessionId); // ps_live_...
```

### Check Session Status

```typescript
const status = await agent.getSession(session.sessionId);
console.log(status.remaining); // remaining budget in base units
console.log(status.chargeCount); // number of charges submitted
```

### Close a Session Early

```typescript
const result = await agent.closeSession(session.sessionId);
// settleTriggered: true — remaining budget is unlocked
```

### Session Lifecycle

1. Agent creates session with budget lock
2. Merchant submits micro-charges (each with PoTE proof)
3. Either the session expires (TTL), agent closes it, or merchant settles
4. All accumulated charges settle in one on-chain transaction
5. Unused budget is unlocked back to the agent

## Error Handling

Both SDKs throw `PieverseError` for API failures:

```typescript
import { PieverseError } from '@pieverse-eng/agent-sdk';

try {
  await agent.authorize(opts);
} catch (err) {
  if (err instanceof PieverseError) {
console.log(err.error);      // e.g. 'insufficient_balance'
console.log(err.statusCode); // e.g. 400
console.log(err.message);    // human-readable description
  }
}
```

### Error Codes

| Code                          | Description                                    |
| ----------------------------- | ---------------------------------------------- |
| `insufficient_balance`        | Not enough balance to authorize payment        |
| `spending_limit_exceeded`     | Transaction exceeds configured spending limits |
| `insufficient_session_budget` | Session budget exhausted                       |
| `challenge_window_expired`    | Strict-mode hold window has passed             |
| `invalid_proof`               | Proof of delivery failed validation            |
| `invalid_request`             | Malformed request                              |

## Gating an Endpoint with Hono Middleware

The simplest way to add a paywall is `middleware402()`, which works with [Hono](https://hono.dev):

```typescript
import { Hono } from 'hono';
import { PieverseMerchant } from '@pieverse-eng/merchant-sdk';

const merchant = new PieverseMerchant({
  apiKey: process.env.MERCHANT_API_KEY!,
  cpBaseUrl: process.env.CP_BASE_URL!,
});

type Env = { Variables: { paymentCredential: string } };
const app = new Hono<Env>();

app.get(
  '/api/weather',
  merchant.middleware402({
amount: 0.01,
decimals: 18,
token: '0x55d398326f99059fF775485246999027B3197955', // BSC USDT
symbol: 'USDT',
chainId: 56,
recipient: process.env.MERCHANT_WALLET_ADDRESS!,
description: 'Weather data — current conditions and 2-day forecast',
  }),
  async (c) => {
const credential = c.get('paymentCredential');

// Settle with proof of delivery
const receipt = await merchant.settle(
  credential,
  {
    type: 'http_response',
    contentDigest: 'sha256:...',
    statusCode: 200,
    timestamp: new Date().toISOString(),
  },
  crypto.randomUUID(),
);

return c.json({ ok: true, data: { temperature: 18 } });
  },
);
```

## Manual 402 Challenges

For non-Hono frameworks, create challenges manually:

```typescript
const challenge = merchant.create402Challenge({
  amount: 0.01,
  decimals: 18,
  token: '0x55d398326f99059fF775485246999027B3197955',
  symbol: 'USDT',
  chainId: 56,
  recipient: '0xYourWallet',
  description: 'Premium API access',
});

// Return 402 with challenge body
// challenge.body contains the paymentRequired object
// challenge.x402HeaderValue is set when x402Config is provided
```

### Challenge Options

| Option             | Type         | Description                                               |
| ------------------ | ------------ | --------------------------------------------------------- |
| `amount`           | `number`     | Payment amount in token units (e.g. `0.01` for 0.01 USDT) |
| `decimals`         | `number`     | Token decimals (18 for BSC USDT)                          |
| `token`            | `string`     | Token contract address                                    |
| `symbol`           | `string`     | Token symbol (optional, defaults to `token`)              |
| `chainId`          | `number`     | Chain ID (56 for BSC mainnet)                             |
| `recipient`        | `string`     | Merchant wallet address to receive payment                |
| `description`      | `string`     | Human-readable description of what's being purchased      |
| `sessionSupported` | `boolean`    | Whether this endpoint supports payment sessions           |
| `x402Config`       | `X402Config` | Enable x402 header compatibility (optional)               |

## Settling Payments

After delivering the service, settle the payment credential with proof:

```typescript
const receipt = await merchant.settle(
  paymentCredential,  // from X-Pieverse-Payment header
  proof,              // Proof of Transaction Evidence (PoTE)
  idempotencyKey,     // unique key to prevent double settlement
);
```

### Proof Types (PoTE)

| Type             | Fields                                                           | Use Case                |
| ---------------- | ---------------------------------------------------------------- | ----------------------- |
| `http_response`  | `contentDigest`, `statusCode`, `contentLength`, `timestamp`      | Standard API responses  |
| `stream_summary` | `model`, `tokenCount`, `finishReason`, `durationMs`, `timestamp` | LLM streaming responses |
| `file_delivery`  | `digest`, `uri`, `sizeBytes`, `timestamp`                        | File downloads          |
| `custom`         | `data` (arbitrary JSON)                                          | Custom proof formats    |

## Payment Sessions

For repeated micro-transactions, sessions aggregate charges into a single on-chain settlement:

```typescript
// Submit a micro-charge against an active session
const charge = await merchant.createSessionCharge(
  sessionId,
  '5000000000000000',  // 0.005 USDT in base units
  proof,
  crypto.randomUUID(),
  'API call #42',
);

// When done, settle all accumulated charges on-chain
const receipt = await merchant.settleSession(
  sessionId,
  crypto.randomUUID(),
);
```

## x402 Compatibility

To support the x402 protocol alongside Pieverse A2A, pass `x402Config`:

```typescript
merchant.middleware402({
  amount: 0.01,
  decimals: 18,
  token: '0x55d398326f99059fF775485246999027B3197955',
  chainId: 56,
  recipient: '0xYourWallet',
  x402Config: {
accepts: [
  { network: 'bsc-mainnet', token: 'USDT', maxAmount: '10000000000000000' },
],
  },
});
```

When `x402Config` is provided, the 402 response includes both:

* The Pieverse A2A challenge body (JSON)
* The `PAYMENT-REQUIRED` header (base64-encoded x402 format)
